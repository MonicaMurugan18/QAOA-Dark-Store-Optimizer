----------------------------------------------------------------
WHY WE SPLIT IT THIS WAY
----------------------------------------------------------------
All 13 fixes are in ONE script. If three people edit the same file
at the same time, the work will be lost.

So we split by SECTION of the script. Each person owns different
sections. Nobody touches another person's section.

   Person A owns  : Section 2 (zones), 3 (products), 4 (demand)
   Person B owns  : Section 1 (candidate stores)
   Person C owns  : Section 5 (travel time), 6 (site distance),
                    plus the new checking code at the end

One more important change for everyone:
   Section 1 (stores) must MOVE to AFTER Section 4 (demand).
   Reason: store capacity is now calculated from total demand, so
   demand must exist first. The INTEGRATOR does this move.

   zone_speed       -> dictionary zone_id -> km/h, made by A, used by C
   sites_df         -> made by B, used by C
   zones_df         -> made by A, used by B and C

Put all four capital-letter settings at the TOP of the file, not
inside the loops.

FIX 1 - DEMAND IS 10 TIMES TOO SMALL   (this is the big one)
----------------------------------------------------------------
Now: each order has only 0.1 to 0.25 items. Not possible.
Cause: the "/ 10" in the mean_demand line in Section 4.
Change:
        ITEMS_PER_ORDER = 5.0
        mean_units = zone_orders * ITEMS_PER_ORDER * sku_share
Check: items per order must come out between 4 and 6.

----------------------------------------------------------------
FIX 5 - PRODUCT SHARES ADD TO 1.18, NOT 1.00
----------------------------------------------------------------
Cause: Dairy has 2 products (milk, eggs) but the full 0.18 Dairy
       share is given to BOTH of them.
Change: divide each category share by the number of products in
        that category. Dairy becomes 0.09 for milk, 0.09 for eggs.
Add this line so it can never break again:
        assert abs(sum(sku_share.values()) - 1.0) < 1e-9

----------------------------------------------------------------
FIX 6 - unit_volume_liters IS NEVER USED
----------------------------------------------------------------
Now: chips (0.15 L) take the same space as water (1.0 L).
Change: add a new column to zone_sku_demand.csv:
        demand_volume_liters = units * unit_volume_liters
Then:   total_volume = sum of that column   <-- GIVE THIS TO B

----------------------------------------------------------------
FIX 8 - POPULATION DENSITY DOES NOTHING
----------------------------------------------------------------
Now: correlation between density and orders is -0.105 (zero).
Change: calculate orders FROM density in Section 2:
        multiplier = commercial 1.30, mixed 1.00, residential 0.85
        orders = density / 60 * multiplier * random(0.90, 1.10)
Check: correlation must be above 0.8.

----------------------------------------------------------------
FIX 12 - demand_std_dev DOES NOT MATCH THE DEMAND
----------------------------------------------------------------
Now: demand uses Poisson, so std must be sqrt(mean). The file
     uses 15-35% of the value instead. These disagree.
Change: demand_std_dev = sqrt(mean_units)

----------------------------------------------------------------
FIX 13 - THE "+1" MAKES ALL DEMAND TOO HIGH
----------------------------------------------------------------
Now: poisson(mean) + 1 adds 1 to every value (20-30% extra).
Change: units = max(1, poisson(mean_units))

FIX 2 - STORES ARE 284 TIMES TOO BIG   (this is the big one)
----------------------------------------------------------------
Now: demand 559 units, capacity 158,673 units.
Problem: every plan fits. So the answer is always "open the one
         cheapest store". There is nothing left to optimise, and
         our whole inventory-allocation part becomes pointless.
Cause: max_sku_units = capacity_sqft * random(8, 12)
       This has no connection to how much anyone actually orders.
Change: delete that line. Calculate capacity from demand instead:
        CAPACITY_SLACK = 2.2
        total_sqft = sum of capacity_sqft over all sites
        daily_capacity_liters[i] = round(
            CAPACITY_SLACK * total_volume * sqft[i] / total_sqft / 25) * 25
Check: capacity / demand must be about 2.2x, not 284x.
       At least 4 stores should be needed to cover everything.

----------------------------------------------------------------
FIX 3b - STORES SIT EXACTLY ON TOP OF DEMAND ZONES
----------------------------------------------------------------
Now: 9 of 10 stores have the same coordinates as a zone, which
     gives 0.00 minute delivery. Not possible.
Change: move each store about 390 m away. A candidate site is a
        PLOT near the area, not the centre of the area:
        SITE_OFFSET_DEG = 0.0035
        angle = 2 * pi * i / number_of_sites
        site_lat = lat + SITE_OFFSET_DEG * cos(angle)
        site_lon = lon + SITE_OFFSET_DEG * sin(angle)
Also rename them: "White Town (plot)" etc.
Note: Person C adds the 3-minute picking time. That is fix 3a,
      not yours. Do not add time here.

----------------------------------------------------------------
FIX 4 - ZONE Z20 CANNOT BE REACHED
----------------------------------------------------------------
Z20 Auroville Fringe has no store within 15 minutes. Nearest is
15.13 minutes. It misses by 8 seconds.
Change: add one more candidate site to the list:
        ("DS11", "Kuilapalayam", 11.9958, 79.8175)
        (real village on the edge of Auroville)
DO NOT fix this by changing the promise to 16 minutes. The
15-minute promise is the main point of our project, and it is also
what keeps the quantum problem small enough to run.

----------------------------------------------------------------
FIX 7 - RENT HAS NO RELATION TO STORE SIZE OR LOCATION
----------------------------------------------------------------
Now: 1,200 sqft costs Rs 76,434 but 2,000 sqft costs Rs 51,023.
     White Town (the most expensive area) is cheap per sqft.
     Correlation between rent and size is only 0.262.
Problem: which store we open is decided by the random number
         generator, not by geography. That is exactly what our
         project is supposed to decide properly.
Cause: rent, setup and size are three separate random numbers.
Change:
        RENT_PER_SQFT_BASE = 35.0
        TOWN_CENTRE = (11.9330, 79.8340)    # White Town
        d = haversine_km(site_lat, site_lon, TOWN_CENTRE)
        premium = clip(1.35 - 0.05 * d, 0.80, 1.35)
        rent  = sqft * RENT_PER_SQFT_BASE * premium * random(0.95, 1.05)
        setup = sqft * random(280, 360)
Check: correlation between rent and sqft must be above 0.8.

----------------------------------------------------------------
FIX 11 - RENT IS MONTHLY, SETUP IS ONE TIME, CANNOT ADD THEM
----------------------------------------------------------------
Our cost formula needs ONE number per store per day.
Change: add a column:
        daily_opening_cost_inr = rent / 30.4
                               + setup / (36 * 30.4)
        (36 months = 3 year plan. Write this in the README.)
